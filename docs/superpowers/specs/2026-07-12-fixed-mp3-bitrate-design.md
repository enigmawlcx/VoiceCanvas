# 工作台 MP3 恒定比特率设计

- 日期：2026-07-12
- 状态：设计已批准，待书面审阅
- 范围：配置页、工作台分段合成、整篇拼接导出

## 1. 背景与目标

当前工作台向 MiniMax 发起语音合成请求时将 MP3 比特率硬编码为 `128000`，但没有启用 MiniMax 的恒定比特率控制。拼接阶段通过 pydub/ffmpeg 解码并重新编码音频，却未指定输出比特率，因此最终文件也不保证使用固定码率。

本次改动需要满足以下结果：

- 配置页可选择 MP3 比特率：32、64、128、256 kbps。
- MiniMax 生成的每个 MP3 分段均使用所选比特率并强制 CBR。
- 工作台拼接生成的最终 MP3 使用相同的固定比特率。
- 一次批量生成任务中的所有分段、失败重试和最终拼接使用同一份音频配置快照。
- WAV 和 FLAC 保持可用，但不应用 MP3 比特率设置。

## 2. MiniMax API 依据

MiniMax T2A v2 的 `audio_setting.bitrate` 仅对 MP3 生效，官方支持值为：

- `32000`
- `64000`
- `128000`
- `256000`

MiniMax 于 2025-09-23 在 `audio_setting` 下新增布尔参数 `force_cbr`。MP3 请求设置 `force_cbr: true` 后，以恒定比特率编码。

比特率不影响文本合成的字符或 token 用量。接口将 `usage_characters` 与 `bitrate`、`audio_size` 分别返回；较高比特率主要增加输出文件大小、传输量和本地存储占用。

官方资料：

- https://platform.minimax.io/docs/api-reference/speech-t2a-http
- https://platform.minimax.io/docs/release-notes/apis

## 3. 方案选择

采用“API 与拼接导出双层强制 CBR”：

1. MiniMax 每段 MP3 请求携带所选 `bitrate` 和 `force_cbr: true`。
2. 最终拼接时，ffmpeg 按相同比特率重新编码为 CBR MP3。

只控制 MiniMax 无法约束重新编码后的成品；只控制最终导出则无法保证单个分段。双层控制是同时满足两个目标的必要条件。

## 4. 配置模型与配置页

### 4.1 配置模型

`AppConfig` 新增 `default_bitrate`：

- 存储单位：bps。
- 默认值：`256000`。
- 合法值：`32000`、`64000`、`128000`、`256000`。
- 由后端模型进行枚举校验，非法值返回明确的 422 参数错误，不静默回退。

旧配置文件缺少该字段时，由配置模型自动采用 `256000`，不执行迁移，也不强制重写配置文件。新安装同样默认使用 256 kbps。

这会有意改变旧版本硬编码的 128 kbps 行为：升级后的用户即使不打开配置页，下一次 MP3 生成也默认使用 256 kbps CBR。

### 4.2 配置页交互

“默认参数”区域新增“默认比特率”选择框，显示：

- 32 kbps
- 64 kbps
- 128 kbps
- 256 kbps

交互规则：

- 格式为 MP3 时允许选择比特率。
- 格式为 WAV 或 FLAC 时禁用选择框，并显示“仅适用于 MP3”。
- WAV/FLAC 状态下保存配置时仍保留上次选择的 MP3 比特率，以便切回 MP3 时恢复。
- `force_cbr` 不作为用户开关。只要格式为 MP3，系统始终启用，避免形成“要求固定比特率但关闭 CBR”的矛盾配置。

## 5. 任务级音频配置快照

工作台开始一次批量生成时，读取并锁定以下配置：

- `format`
- `sample_rate`
- `bitrate`

每个分段请求、失败分段重试和最终拼接请求都显式携带同一份快照。任务进行期间即使用户修改全局配置，当前任务也不会混入新参数。

后端对快照进行独立校验：

- 格式仅允许 `mp3`、`wav`、`flac`。
- 采样率仅允许 MiniMax 官方支持的现有枚举值。
- MP3 比特率仅允许四个官方值。

为兼容已有调用方式，新增快照字段保持可选；缺少时读取当前全局配置。新工作台流程必须显式传递快照。

## 6. 合成与拼接数据流

### 6.1 MiniMax 分段合成

MP3 的 `audio_setting` 包含：

```json
{
  "sample_rate": 32000,
  "bitrate": 256000,
  "format": "mp3",
  "channel": 2,
  "force_cbr": true
}
```

其中示例码率由任务快照决定，并非再次硬编码。

WAV/FLAC 请求不发送 `bitrate` 和 `force_cbr`，因为这两个设置只适用于 MP3。其他现有语音参数和双声道规则不变。

单段接口直接返回 MiniMax 音频，因此 MP3 分段本身即为目标码率的 CBR 文件。

### 6.2 拼接导出

拼接仍按现有流程解码分段、在相邻分段间插入 500ms 静音并重新编码：

- MP3：明确传入任务快照中的比特率，并使用 ffmpeg 的 CBR 编码参数。
- WAV/FLAC：按现有无损格式导出，不套用 MP3 比特率。

`/synthesize/full` 后端整篇合成和前端逐段生成后调用 `/synthesize/concat` 两条路径必须复用同一个导出函数，并传入相同的格式、采样率和比特率语义，避免行为分叉。

## 7. 接口调整

工作台的分段、整篇与拼接请求模型增加可选音频快照字段。字段缺省时使用服务端当前配置，以保持向后兼容。

前端批量生成流程在开始时建立快照，后续调用不得重新从配置页或服务端获取这些参数。失败重试必须复用原任务快照，而不是读取重试时的全局配置。

单次手动试听如果不属于已有批量任务，则在该次操作开始时创建自己的配置快照。

## 8. 错误处理

- 非法配置值由后端模型拒绝，返回 422，不自动替换为其他码率。
- 旧配置缺少 `default_bitrate` 时采用 `256000`；这属于缺省值处理，不属于非法值回退。
- WAV/FLAC 保留配置中的比特率值，但合成和导出均不应用该值。
- MiniMax 请求失败沿用现有错误分类和失败分段重试机制。
- ffmpeg 导出失败时不返回成功文件路径，对外返回可理解的“音频导出失败”错误并保留底层异常用于诊断。
- 不以播放器或文件扩展名作为 CBR 验收依据，必须检查实际编码结果。

## 9. 测试与验收

### 9.1 自动化测试

- 配置模型：默认 256 kbps、四个合法值、非法值拒绝、旧配置缺字段兼容。
- 设置 API：读取和保存 `default_bitrate`。
- 配置页静态/交互测试：MP3 可选择；WAV/FLAC 禁用并显示提示；保存载荷包含正确值。
- MiniMax payload：MP3 包含指定 `bitrate` 与 `force_cbr: true`；WAV/FLAC 均不包含。
- 工作台：批量生成、失败重试和拼接使用同一快照。
- 服务层：`synthesize_full` 和 `concat` 两条路径均向导出层传入目标比特率。
- 回归：双声道、500ms 段间静音、分段失败处理与既有格式导出保持正常。

### 9.2 音频实测

生成短 MP3 分段并完成拼接后，使用 ffmpeg/ffprobe 等效方式检查：

- 每个分段的目标码率与配置一致。
- 每个分段采用 CBR 编码。
- 最终文件的目标码率与配置一致。
- 最终文件采用 CBR 编码。
- 文件时长包含原音频时长及每个分段间的 500ms 静音。

播放器显示的平均码率只能作为辅助信息，不能替代编码检查。

## 10. 非目标与风险

本次不增加 VBR、ABR、编码器质量档位或自定义任意码率，也不改变 MiniMax 计费统计。

256 kbps 相比原硬编码的 128 kbps 会使同等时长 MP3 的文件体积大约翻倍，但不会增加 TTS 字符/token 用量。由于源语音质量、采样率和双声道复制方式可能成为质量上限，256 kbps 不保证听感相对 128 kbps 出现明显提升；其价值主要是满足用户指定的高码率和一致编码要求。
