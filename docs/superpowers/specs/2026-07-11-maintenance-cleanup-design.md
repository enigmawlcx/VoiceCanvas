# VoiceMax 遗留问题修复设计

- 日期：2026-07-11
- 状态：已确认，待实施
- 范围：测试隔离、文档一致性、测试警告与发布验证

## 1. 背景

现有功能缺口计划中的 Phase 0–4 已基本落地，但仓库仍存在三类遗留问题：测试会意外访问真实 macOS Keychain；历史计划与当前代码状态互相矛盾；测试套件仍产生依赖和音频工具探测警告。此外，受限执行环境禁止绑定本地端口，使端口测试在沙箱中失败，需要与真实产品缺陷明确区分。

## 2. 目标

1. 测试不得读取或修改用户真实 Keychain。
2. 当前状态文档必须与代码、测试数量和已完成功能一致。
3. 在不进行无关依赖升级的前提下，消除能够由项目自身控制的测试警告。
4. 用分层验证区分代码缺陷、测试设计问题与执行环境限制。

## 3. 非目标

- 不新增产品功能。
- 不重构 FastAPI、pywebview 或原生前端架构。
- 不因 Starlette 弃用警告盲目升级核心依赖。
- 不为了适配沙箱而修改 `find_free_port()` 的生产行为。
- 不重写历史实施计划中的逐步操作记录；仅明确其历史属性。

## 4. 方案

### 4.1 测试隔离

在 Settings API 测试的 `client` fixture 中统一替换 `app.api.settings.get_api_key`，使所有通过该 fixture 发起的请求默认获得空密钥。需要模拟已配置密钥的测试继续在测试内部覆盖该替换。

该修复位于测试边界，而不是在生产代码中吞掉 Keychain 错误。真实应用仍应暴露系统 Keychain 故障，测试则不再依赖开发机状态。

### 4.2 文档一致性

- 将 `2026-07-10-voicemax-improvement-backlog.md` 定位为已完成的历史路线图，更新现状摘要，把 A1–A10 等条目标注为已解决，并单列仍有效的问题。
- 修改主设计文档正文中的 CodeMirror、ECharts、系统 ffmpeg 和 `web/vendor/` 等旧描述，使正文直接反映 as-built 架构；附录保留为历史决策说明。
- 更新 README 功能摘要，覆盖周趋势、费用估算、失败段重试、音效器和 clone prompt。
- 在 Studio 设计文档中区分“静态脚本检查”与“真实 DOM/交互自动化测试”。
- 给两份历史实施计划增加状态说明，不机械修改原始 TDD 步骤的 checkbox。

### 4.3 测试警告

`pydub` 警告源于模块导入时尚未设置 `AudioSegment.converter`。优先检查是否可以在导入 `pydub` 前设置 imageio-ffmpeg 路径；若会增加副作用或破坏打包，则使用精确的 pytest warning filter，并在文档中说明原因。

Starlette 的 `TestClient` 弃用警告来自当前 FastAPI/Starlette 依赖组合。先记录为上游兼容性债务，不在本轮升级依赖；只有存在不改变运行时依赖的官方迁移方式时才调整测试客户端。

### 4.4 端口测试

`find_free_port()` 在受限沙箱中因禁止 socket bind 而失败，但该操作是桌面应用启动的必要行为。完整验收分为：

- 沙箱内运行除端口绑定测试外的全部测试；
- 在允许本地 socket 的普通 macOS 环境运行完整测试；
- 若无法获得该权限，明确报告“代码验证通过、环境相关测试未验证”，不得宣称完整测试全绿。

## 5. 实施顺序

1. 用当前失败测试复现 Keychain 泄漏，完成测试隔离并执行 Settings 定向测试。
2. 更新历史 backlog、主设计、README、Studio 测试说明和历史计划状态。
3. 调查并处理 pydub 警告；记录 Starlette 兼容性债务。
4. 执行定向测试、沙箱可运行测试和完整测试，逐项记录结果。

## 6. 验收标准

- Settings API 测试不调用真实 Keychain，在无 Keychain 权限环境中仍能通过。
- 文档不再同时声称同一功能“未实现”和“已完成”。
- 主设计正文与实际 textarea、SVG、imageio-ffmpeg 架构一致。
- README 准确列出当前核心能力。
- pydub 警告已消除或有精确、可验证的保留理由。
- Starlette 警告被明确记录，未通过未经验证的依赖升级掩盖。
- 验收报告明确区分通过项、失败项和环境受限项。

## 7. 风险控制

- 测试隔离只改变测试 fixture，不降低生产环境错误可见性。
- 文档更新以当前代码和测试为证据，不将计划描述当作实现事实。
- 每次只处理一个根因，完成定向验证后再进入下一项。
- 不修改用户现有功能行为，不引入新前端或后端依赖。
